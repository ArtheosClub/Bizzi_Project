## Step 2 — What the RKM Is Structured To Do

### 2.1 Stated purpose

RKM-01 declares itself "the single semantic source of truth for how the
Bizzi Platform repository is organized." Its central thesis (§02) is:

> Knowledge precedes information. Information precedes documents.
> Documents precede folders. Folders never define meaning; meaning
> defines folders.

The operational consequence it draws is unusually strong: **filesystem
layout should be a generated, regenerable output of the semantic model,
not a thing maintained by hand** (§04, §11). Where the filesystem and
the model disagree, the model declares the filesystem wrong.

### 2.2 What it actually contains

| Section | Content |
|---|---|
| §05 | **9 Semantic Domains** — Constitutional, Architectural, Engineering Process, Implementation Pattern, Planning & Sequencing, Illustrative, Codebase, Platform Vision, Reference |
| §06 | **8 Layers**, explicitly mapped onto DECISION_0002's Tier 0–6 structure, plus one new non-authoritative Reference layer |
| §07 | A **10-field classification schema** per artifact, 8 worked examples, and **6 artifact types** (Normative, Interpretive, Generated, Operational, Historical, Reference) |
| §08 | Ownership model — semantic owner vs. constitutional owner, per domain |
| §09 | 3 relationship types (derives-from, illustrates, cross-references) |
| §10 | **12 artifacts declared to be generated** from the model — Repository Structure, Navigation, Index, Migration Plan, Filesystem Layout, Document Placement, Cross-reference Map, Ownership Matrix, Repository Catalog, Knowledge Graph, AI Context Model, Future Search Model |
| §12 | **7 migration-readiness criteria**, all of which must hold before anything is physically moved |

RSM-01 then derives from it: 9 Root Domains, subdomains, a canonical
placement hierarchy, a numbering policy (§07), a namespace analysis of
the real filesystem (§08), a current-root→target mapping (§10), and a
structural validation (§11) that honestly reports **three FAILs**.

### 2.3 Completeness relative to design intent

This is the crux. Of the 12 artifacts RKM-01 says should be generated,
**zero exist in generated form.** RKM-01 §10 states this plainly. Of the
7 migration-readiness criteria in §12, **criterion 1 — "RKM-01 is
approved, not merely drafted" — has never been satisfied**: the document
still carries `Status: DRAFT — Not yet approved for generation`, 2 days
after creation, and RSM-01 is DRAFT *because* RKM-01 is DRAFT.

So: the model is intellectually complete as a design, and operationally
inert. It describes a system for generating repository structure, and
that system does not exist and has not been started. RSM-01 §14 concedes
this: the models "stand as valid models" but block "the next step."

## Step 4 — Independent Audit

### 4.1 Is the RKM kept current, or has it drifted?

**It has drifted, and the drift is demonstrable, not inferred.** Five
independent pieces of evidence:

**(a) One commit, ever.** RKM-01 was created 2026-07-24 07:36 and has
never been edited. In the 2 days since, 5,092 lines of new governance
material across 28 files were produced. None of it touched the document
that claims to be "the single semantic source of truth for how the
repository is organized."

**(b) Five new root domains it does not classify.** The unmerged stack
introduces `40_GATE_C/`, `45_GATE_C_TRANSITION/`,
`50_EPOCH_IV_IMPLEMENTATION/`, `60_MODULE_SPECIFICATIONS/`, and
`70_ENGINEERING_SPECIFICATIONS/`. RKM-01 §05 asserts its nine domains are
"sufficient to classify every artifact currently in the repository."
That assertion was true when written and is now stale — and RKM-01 is
carried onto those very branches byte-identical, meaning the work that
created the new directories never once consulted or amended the model
that was supposed to govern their placement.

**(c) A brand-new numbering collision of exactly the class RSM-01 had
already documented.** RSM-01 §08 flagged `06_PLAYBOOKS` vs `06_REFERENCE`
as a "namespace collision risk." Two days later,
`50_EPOCH_IV_IMPLEMENTATION/` was created alongside the pre-existing
`50_IMPLEMENTATION/` — a second `50_` prefix. The documented lesson did
not survive 48 hours. (Verified: prefixes `00_`, `06_`, and `50_` are all
now shared by multiple root directories; `00_` is shared by four and was
never flagged at all.)

**(d) Every one of the five new directories violates RSM-01's own
reserved-range policy.** RSM-01 §07 reserves `40–49` for Reference and
`50–99` for Platform. Actual usage: `40_GATE_C` and `45_GATE_C_TRANSITION`
are Planning/Gates content sitting in the Reference range;
`50_EPOCH_IV_IMPLEMENTATION`, `60_MODULE_SPECIFICATIONS`, and
`70_ENGINEERING_SPECIFICATIONS` are Engineering/Planning content sitting
in the Platform range. Five for five.

**(e) A stale count inside a section that was itself updated.** RSM-01
§08 states "131 loose root-level `.md` files." The actual current count
is **129**. The two-file difference is `TEST_WRITE.md` and
`CONNECTOR_TEST.md`, deleted under RTC-01 — and §08's own row *about
those deletions was updated in that same commit* while the total two rows
below it was not. This is drift inside a single table, introduced by the
edit that was supposed to keep the table current.

### 4.2 Does the RKM's account of "what's been done" match reality?

Mostly yes, with two discrepancies:

**Discrepancy 1 — a §10 "generated artifact" was hand-authored
elsewhere.** RKM-01 §10 lists *Repository Index* as Generation Status
"Not yet generated." But `50_IMPLEMENTATION/REPOSITORY_RELEASE_REPORT.md`
§Step 6 is titled **"Repository Index"** and contains one — hand-written.
RKM-01 §07.3 defines Generated artifacts as "produced from a normative
source, **never hand-authored** once generation exists." Generation does
not yet exist, so this is not a rule violation in the strict sense — but
it is the model losing track of its own output: an artifact it claims
ownership of was produced outside it, by a different document, without
either noticing.

**Discrepancy 2 — a broken cross-reference, in the Gate C package, to a
section that does not exist.** `40_GATE_C/GC-001_GATE_C_CHECKLIST.md`
(requirement GC-F-06) and `40_GATE_C/GC-002_EVIDENCE_REGISTER.md`
(evidence EV-F-06) both cite **"RSM-01 §07.3 (Artifact Types)."**
RSM-01 §07 is *Repository Numbering Model* and has no §07.3 at all.
Artifact Types is **RKM-01 §07.3**. Verified by direct header inspection
of both files.

This last one deserves emphasis, because of what it implies. GC-001's own
requirements **GC-C-04** ("every file path cited in an in-scope document
resolves") and **GC-F-04** ("no broken link exists within the in-scope
document set") are precisely the checks that would have caught this. They
did not catch it because **all 49 GC-001 requirements carry Status `NOT
REVIEWED`** — the checklist was authored but never executed. A
certification package shipped with a broken citation to the very
document whose classification scheme it was citing, inside a requirement
row designed to detect broken citations.

Everything else checks out: 102 root `PB0*.md` files ✓, 14 `CORE_*.md` ✓,
`06_PLAYBOOKS/` still contains only `.gitkeep` ✓, both content-divergent
duplicate pairs (`GOVERNANCE_MODEL.md`, `CAPABILITY_MAP_v1.0.md`) still
present ✓, all three RSM-01 §11 validation FAILs still accurate ✓.
RSM-01's honesty about its own failures is genuinely a strength.

### 4.3 Is the RKM part of the documentation-volume problem, or a control on it?

**Currently it is part of the problem, though it was designed to be the
cure.** The evidence is a single number:

> **Documents outside RKM-01/RSM-01 that actually use RKM-01's
> classification schema (its 9 domains or 8 layers) to classify
> anything: ZERO.**

Verified by grep across the entire stack tip. The only other files
mentioning "Knowledge Domain" or "Semantic Domain" are three
Art-of-Business platform-vision documents using the terms in an unrelated
sense.

Breaking down how today's 28 new files reference it:

| Directory | Files referencing RKM-01/RSM-01 | Total files |
|---|---|---|
| `40_GATE_C/` | 3 | 5 |
| `45_GATE_C_TRANSITION/` | 1 | 1 |
| `50_EPOCH_IV_IMPLEMENTATION/` | **0** | 4 |
| `60_MODULE_SPECIFICATIONS/` | **0** | 15 |
| `70_ENGINEERING_SPECIFICATIONS/` | **0** | 3 |

And the four that *do* reference it cite it only as **evidence of known
repository disorder** (RSM-01 §08's collision and duplicate findings) —
never as a classification authority. Not one document says "this artifact
is Domain X, Layer Y per RKM-01."

The deeper finding is what happened in that zero. On 2026-07-26, three
new framework layers were built — Epoch IV Engineering Governance, the
Module Specification Framework, and the Engineering Specification
Framework. **Each independently invented its own classification,
lifecycle, and status vocabulary**: RKM-01 has Lifecycle
(Draft/Active/Superseded/Historical); the Module framework introduced
Status/Review/Approval/Implementation/Verification/Gate-D; the Outstanding
Items Register introduced Open/Accepted/Deferred/In Review/Closed plus a
9-value Decision enum; the Engineering framework introduced its own
Status again. **Four overlapping lifecycle vocabularies now exist, none
reconciled to the model whose stated job was to be the single source of
truth for exactly this.**

RKM-01 did not prevent that proliferation. It did not even register it.
A control that nothing consults is not a control — it is one more
document competing for the reader's attention, and by its own §06 it is
explicitly non-authoritative, which means it has no mechanism to compel
its own use.

**One genuine credit**, and it is not small: RKM-01 §12 and RSM-01 §13
did their job. They gated a large, risky, repo-wide file migration behind
seven objective criteria, and that migration correctly **never
happened**. Had RKM-01 been a more aggressive document, the repository
might now be mid-reorganization on top of everything else. The restraint
was correct.

## Step 5 — Repository Optimization for Coding

Ranked by what most directly unblocks writing Gate C code with
confidence. None of these require adopting or rejecting RKM-01.

**1. Fix the stale-stack docs on `main` — highest value per unit of
effort.** `docs/c4/C1_CONTEXT.md`, `C2_CONTAINER.md`, `C3_COMPONENT.md`,
`docs/c4/README.md`, and `docs/adr/README.md` currently describe
NestJS/TypeScript/Prisma **as the current stack** on `main`. Any
developer — human or AI — who reads the architecture docs before writing
Gate C code gets actively wrong information. The corrected versions
already exist on PR #2. This is the single most dangerous thing in the
repository for someone about to write code.

**2. Resolve PR #2, one way or the other.** It is 59 commits behind and
conflicted in exactly 2 files (`CLAUDE.md`,
`GATE_C_ARCHITECTURE_DECISION_PROPOSALS.md`). Its other 7 files apply
cleanly and include fix #1 above. Either land it or explicitly close it
and cherry-pick the C4 rewrites — but it should not stay open another
week degrading.

**3. Land or close the 5-branch governance stack.** 5,092 lines across 28
files, zero PRs. Because the branches are strictly linear, one PR from
`agent/engineering-specifications` to `main` carries all of it. Right now
this work is invisible to review and duplicated in every branch's history.

**4. Stop creating new numbered root directories until numbering is
settled.** Prefixes `00_`, `06_`, and `50_` are each shared by multiple
directories. Five new roots appeared in one day, all violating the only
written numbering policy. A one-line rule in `CLAUDE.md` ("no new
top-level numbered directory without an explicit decision") costs nothing
and stops the bleeding.

**5. Decide the four competing lifecycle vocabularies.** Before Gate C
code lands, pick one status vocabulary for work artifacts. Four is not a
governance system; it is four governance systems.

**6. Push the `implementation-baseline-v1.0` tag or accept losing it.**
It exists only as a local object in an ephemeral container; the remote
has zero tags. It will be gone when this container is reclaimed.

**7. Do not run an RKM-driven migration now.** Moving `backend/` would
break CI paths, import roots, and Docker build context (RSM-01 §10 rates
it High risk and defers to EGC-01). Reorganizing the filesystem
immediately before writing the first domain models is the worst possible
sequencing.

## Step 6 — Most Direct Path to a Working MVP

I think scope needs cutting, not just reorganizing. Concretely:

**Cut, or defer past MVP:**

- **The AI/agent module (MS-007) as a Gate C dependency.** It is blocked
  by GC-001 (unapproved) and ADW-05 (unwritten), and those two block 9 of
  Gate D's 10 work packages. This is the project's stated critical path —
  and it is also the most speculative part of the product. An MVP that
  demonstrates workspace-scoped business objects, tasks, and audit with
  *no* agent orchestration is still demonstrable. One that waits for the
  Provider/Model catalog is not demonstrable for weeks.
- **GC-002 through GC-010.** Of the ten open proposals, only GC-001
  genuinely blocks the critical path. Several others (GC-009 retention
  policy, GC-010 benchmarking, GC-005 404 semantics, GC-007 audit diff
  representation) are refinements that can be decided *after* the first
  models exist, when the decision is concrete rather than hypothetical.
  Deciding all ten before writing a line is a false prerequisite.
- **The Engineering Specification Framework layer (`70_`), for MVP
  purposes.** It requires a 29-section implementation contract per module
  before that module may be coded. For 12 modules that is a very large
  document set standing between now and the first `CREATE TABLE`. Keep it
  for post-MVP; for MVP, the Module Specification plus the relevant ADR
  is sufficient contract.

**Do, in this order:**

1. Fix the C4/ADR-index stack staleness (Step 5 item 1).
2. Approve **GC-001 only**, or explicitly defer the agent module out of
   MVP scope — either unblocks progress; leaving it open blocks
   everything.
3. Write the first vertical slice: `Workspace` → `WorkspaceMembership` →
   one `EnterpriseObject`-class entity, with `workspace_id` scoping and
   audit, end to end — model, migration, repository, service, endpoint,
   test. The architecture for this is *already fully decided* (ADR-0003,
   0004, 0005, 0006; D01–D10; the isolation review). Nothing blocks it
   today.
4. Demo that slice against WP04's acceptance criteria. That is the
   earliest point the project produces evidence rather than plans.

The honest summary: **the MVP is not blocked by missing decisions. It is
blocked by the decision to keep making decisions.** Every architectural
input the first vertical slice needs already exists and is approved.

## Step 7 — Longer-Term Knowledge Management

**Worth keeping:**

- **The core RKM insight** — that an artifact's meaning should not be
  determined by where it happens to sit. That is correct and will matter
  more as the corpus grows past 581 files.
- **RSM-01 §08's namespace analysis.** It is the most immediately useful
  thing in either document: a concrete, verified list of real repository
  defects. It found genuine problems and did not pretend to fix them.
- **The §12 readiness gate.** It prevented a risky migration. Keep this
  pattern for any future structural change.
- **The Layer↔Tier mapping (§06).** Reusing DECISION_0002's tiers rather
  than inventing a parallel hierarchy was the right call, and is the one
  place the RKM successfully avoided vocabulary proliferation.

**Over-engineered for where this project actually is:**

- **The 12 generated artifacts (§10).** Knowledge Graph, AI Context
  Model, Future Search Model, Repository Catalog, Ownership Matrix — for a
  repository with 283 lines of shipped Python. Zero of the twelve exist,
  and none of the twelve would make the first vertical slice easier to
  write. This is tooling for a mature corpus, specified before the corpus
  has a product.
- **The 10-field classification schema (§07.1).** Ten fields per
  artifact, across 581 artifacts, hand-maintained (no generation exists),
  is roughly 5,800 field values to keep current. That will not be
  maintained. Three or four fields (Domain, Lifecycle, Owner, Authority
  Source) would capture most of the value at a fraction of the cost.
- **The generate-the-filesystem-from-the-model ambition (§04, §11).**
  Elegant, and genuinely the right long-term direction for a large
  knowledge corpus — but it presupposes tooling that does not exist,
  will not be written during MVP, and whose absence RKM-01 §11 already
  concedes leaves the filesystem "manually maintained."

**What I would actually do, post-MVP:**

Demote RKM-01 from "single semantic source of truth" to what it honestly
is today — a **classification convention plus a repository-defect
register**. Merge RSM-01 §08 (namespace analysis) into it, cut §10 from
twelve generated artifacts down to the two that would genuinely help
(Repository Index, Cross-reference Map), and reduce §07.1 to four fields.
Then, critically, **give it one enforcement hook**: a CI check that fails
when a new top-level directory appears without a corresponding RKM entry.
A knowledge model with one automated check that runs is worth more than a
complete model that nothing consults — which is precisely what the last
two days demonstrated.
